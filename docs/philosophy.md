# 核心思想：需求即提示词

**把需求说清楚，提示词就写好了。** 好提示词不是咒语，而是一段写清楚的需求：做什么、对谁、达成什么、怎么验收。需求被写清楚的那一刻，提示词就已经存在了。

- **核心需求**：一条用过的好提示词不该随一次对话消失，要能被复用。
- **目标**：任何场景下，把核心需求与目标简洁说清楚，就得到一条可直接粘贴的提示词。

这套思想在项目里落成两件事：

1. **体例即模板**——全库每条提示词都按同一句法写：第 1 句说做什么/对谁/达成什么，第 2 句给做法与约束，第 3 句说交付物与验收方式。一条提示词读完就是一份需求说明书，不需要再翻译。
2. **提炼即需求**——入库时把原始对话里的具体路径、课题、代号换成通用说法（目标期刊、目标平台），把散在多轮里的要求收敛成一段话：脱敏不损失指令力，泛化不损失指令力，复制即可粘贴。

因此判断一条提示词好不好，看的不是它多花哨，而是**读者读完是否清楚要做什么、做到什么程度算完成**。

## 五条判断标准

「需求即提示词」落到每一条上，是五条可对照检查的标准。写新条目、审校旧条目都按这五条过：

1. **直击问题**——第 1 句直接说要解决什么，不做铺垫，不写「为了……所以」「让后续优化有据可依」这类目的性铺垫。
2. **直击目标**——写明做到什么程度算完成：目标、范围与验收标准都落在正文里，读者不必从做法反推想要什么。
3. **简洁易懂**——用平实说法，不堆术语与直译比喻（体检、抓手、闭环、颗粒度之类），不写「全面」「系统」「深入」「高效」这类空泛词，不在相邻两句里重复同一个词。
4. **复制即用**——不设占位符：正文里不出现 XXX、待填、〈文件名〉、「相关文件」这类要用户填空或回指上文的地方；需要指明对象时在句内写死具体对象（如「用 Python 绘制」「按目标期刊的公开写作要求」「保留最近 7 份」）。
5. **不绑定具体项目**——原始对话里的路径、课题、代号都换成通用说法，脱敏与通用化都不损失指令力。

前两条管「说清需求」，第三条管「读得懂」，后两条管「拿去就能用」。五条都守住，一条提示词才算写完。

## 内容体例

这套体例就是「需求即提示词」的落地形式：先把需求与目标说清楚，再给做法与验收。写一条提示词时遵循这三条：

1. **标题**：动宾短语，6~12 字，独立可懂，不与正文首句重复
2. **正文**：按「动作 + 对象 + 范围 → 做法/标准 → 交付物」组织成**一个自然段的 2~3 句**，不用占位符，复制即可直接粘贴
3. **可读性**：正文总长不超过 100 字（实测 65~100 字，中位数 92）；单句不超过 55 字；顿号连排不超过 4 项，超过就按语义分组并用分号衔接

正文的三句分工是固定的：**第 1 句**是需求本身——做什么、对谁、**达成什么**；**第 2 句**给做法与约束；
**第 3 句**说交付什么、怎么验收。整段不换行分段。

判断标准：把这条提示词单独发给一个不了解上下文的智能体，它能不能说出「我要什么」和「做到什么算完成」。说不出来，就是第 1 句没写需求。

| 写法 | 判断 |
| --- | --- |
| 「让同一件事只有一处实现。找出重复来源与职责交叉处，用调用关系确认后再合并。」 | 好：需求与目标在前，做法在后 |
| 「找出重复劳动来源，定位职责交叉与边界不清的位置，用调用关系证实。」 | 不好：只有方法，达成什么要靠猜 |
| 「审计插件体系。」 | 不好：标题复述，等于没说需求 |

避开的写法：

- **目的性铺垫**——「让后续优化有据可依」「便于他人复现」「便于下一轮直接接续」「让文件位置一目了然」。目的若值得保留，压成动词短语（如「提高命中率」「保证可复现」）。
- **只有方法的命令**——第 1 句只写做法或复述标题，需求与目标让智能体从上下文猜。改写成「让 X 达成 Y，……」。
- **诱导绕过的命令**——「把失败用例修到通过」这类要求可以被跳过用例满足，写成「让测试真实通过而不是被跳过」。
- **连续否定**（「不…不…不…」）、**空泛词**（全面 / 系统 / 深入 / 高效 / 完善 / 优化）。
- **句尾用「等」兜底**、**顿号并列超过 4 项**、**同一件事说两遍**。

标签 2~3 个用于检索。

一个完整的条目长这样：

```markdown

```

## 按需保留两种表达

正文已经足够简洁（当前全库 555 条都带简洁表达，实测 17~38 字、中位数 27 字），或两种说法一致时，卡片只显示正文和一个复制按钮。确有详略价值的条目才同时提供两种说法，各有一个复制按钮：

| 标题 | 详细表达 | 简洁表达 |
| --- | --- | --- |
| 整理会议纪要 | 没开会的人读纪要就能接上进度。先写已确认结论，再列行动项并注明负责人、交付物及截止时间，未明确的负责人或日期标为待确认。交付纪要与需确认条目，末尾单列未决问题与下次跟进。 | 把会议记录整理为结论、行动项和未决问题，行动项标明负责人和期限。 |
| 归档废弃与无关文件 | 让工作区只剩在用的内容，废弃文件可回溯地归档。按引用关系分类：在用保留，无关移入归档目录，待确认列出。移动后更新受影响路径与配置，交付移出清单与保留项，附引用修改与回溯方式。 | 把废弃和无关文件移入归档目录，按引用关系分类后更新受影响路径。 |
| 定位瓶颈并加索引 | 让慢查询变快且不拖慢写入。先用执行计划定位瓶颈，记录数据规模、筛选条件及排序方式，再定索引列与联合索引顺序，权衡写入开销与索引占用。交付瓶颈证据与索引变更，附前后耗时对比和不适用场景。 | 用执行计划找准慢查询的瓶颈，补索引提速且不拖慢写入。 |

- **提示词正文**（`<!-- s: -->` 之后的内容）：每条必填；没有简洁表达时，这就是唯一版本
- **简洁表达**（`<!-- s: -->` 里）：可选；同一件事的更短说法，保留全部指令力，可直接粘贴

`<!-- s: -->` 里的文字必须**是提示词本身**，不是对提示词的描述。与正文一致时不要保留该字段。
