# 提示词文案改写规范（第二轮）

目标：每条提示词**一眼就知道要干嘛**——第一句点明动作与对象，做法说清关键约束，
最后一句说清交付什么、怎么算完成。不铺垫、不解释为什么这么写、不说套话。

## 硬性格式

| 项 | 要求 |
| --- | --- |
| 标题 | 动宾短语，6~12 字；全库唯一；合并后条目按新职责重新命名 |
| 正文 | **一个自然段**（段内不换行），2~3 句，总长 **60~95 字**，硬上限 100 字 |
| 第 1 句 | 做什么 + 对谁/对象 + 达成什么 |
| 第 2 句 | 怎么做、遵守哪些约束（2~3 个要点合并成一句，以正向表述为主） |
| 第 3 句 | 交付什么 + 怎么验收 |
| 简洁表达 `<!-- s: -->` | 20~38 字，必须是**可直接粘贴的指令句**（不是对提示词的描述），与正文实质不同；正文已足够短（< 60 字）时**删掉该字段**，只留正文 |
| 标签 | 2~3 个，用于检索；沿用原标签或换成更贴切的 |

`<!-- id: -->` **原样不动**——它决定收藏与分享链接指向哪一条。

## 必须删掉

- **目的性铺垫句**：「让后续优化有据可依」「便于他人复现」「便于下一轮直接接续」
  「让文件位置一目了然」「让重复访问不再穿透到后端」「让接手的人靠文档看懂」……
  目的若值得保留，压成动词短语（如「提高命中率」「保证可复现」）。
- **连续否定**（「不…不…不…」）、**空泛词**（全面 / 系统 / 深入 / 高效 / 精细 / 完善 / 优化）。
- **句尾用「等」兜底**、**顿号并列超过 3 项**（超过就按语义分组，用分号衔接）。
- **与标题重复的措辞**、**同一件事说两遍**、对交付物的泛泛形容。

## 必须保留

- **具体约束与具体交付物**：可检查的要求一个都不能丢（「修复后补回归测试」
  「交付修改位置与验证结果」「列出未覆盖分支」）。
- **占位符**：`[方括号]`，与正文连写**不加空格**（`升级[依赖]到[版本]`）。
- **脱敏**：不出现具体项目名、课题、期刊、工具名、身份、本机路径、内部代号。
  期刊写 `[目标期刊]（如 PRL / PRB）`，格式写 `[写作格式]`，语言写 `[编程语言]`，
  工具写「项目规范文件（如 CLAUDE.md）」。
- **合并条目的独有要点**：被并条目的原文见 `_tools/archive/merged_absorbed.md`，
  对应主条目必须吸收其中独有的验收点，不能只留主条目的原意。

## 改写示例

**改前**（98 字，有铺垫、有空泛词、交付物罗列过细）：

> 为[模块]的关键路径建立基准测试，让后续优化有据可依。固定输入规模、运行环境与重复次数，
> 记录耗时与内存占用，保留多次测量数据以区分趋势与波动。交付基准代码、运行方法、原始结果与汇总表。

**改后**（78 字，去掉铺垫，保留可检查的约束）：

> 为[模块]的关键路径建立基准测试。固定输入规模、运行环境与重复次数，记录耗时与内存占用，
> 多次测量以区分趋势与波动。交付基准代码、运行命令与原始结果。

**改前**：

> 实现[项目/功能]，解决[具体问题]，面向[目标用户]。先核对现有结构、运行方式与约束，
> 选简单可维护的方案，不为局部需求引入多余依赖。交付改动说明、使用方式、验证结果与已知限制，
> 标出需要人工确认的部分。

**改后**：

> 实现[项目/功能]，解决[具体问题]，面向[目标用户]。先核对现有结构与约束，按项目风格选最简方案。
> 交付改动清单、使用方式与验证结果。

## 边界

- 只改分配给你的文件；不新增、不删除条目（合并与分类重排已由脚本完成）。
- 不改 `<!-- id: -->`；不调整条目顺序；不改文件 frontmatter。
- 不要运行 `python build.py`（`dist/` 由其他会话统一构建）；不要改 `src/index.html`、
  `src/assets/`、`build.py`、`_tools/*.py`。
- 改完自查：正文 60~95 字（≤100）、无空泛词、无连续否定、简洁表达短于正文。
